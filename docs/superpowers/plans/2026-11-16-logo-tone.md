# The logo in the tone its picture needs: implementation plan

Spec: `docs/superpowers/specs/2026-11-16-logo-tone-design.md` (revised at `ceae4698`). Branch `qafix/logo-tone`, merged with `qafix/integration` (`a352e38e`) at `ea631148`. Written 16 Nov 2026. Nothing in this plan is built yet.

Goal: every design carries a logo file of the client's (the stored file, the brand's own second file, or a recolored copy the client's own posts show), and no design is sent back because the model drew the logo in a tone the client's posts use.

How it is built: one pure module decides everything (`logoTone.ts`, with the making rule beside it in `logoCopies.ts`). The picture service gains two routes and a second shape of the locate request. The lifecycle's `design_settings` step makes each client's set with no model call. A job copies the set into its input, the worker sends templates to locate and stamps the file locate named. The settings card shows the set.

Stack: TypeScript on Deno (edge functions) and Node 22 (picture service, sharp, zod, hono), Postgres (PGlite in tests), React, vitest.

## Rulings

Where the spec leaves a choice open or does not fit the code after the merge. Each is written as what, why, and the cost if it is wrong.

1. What: a part is a set of ink pixels joined by flood fill, where two neighbors join when they differ by at most 16 in each channel. The spec's wording ("every two pixels that share an edge differ by at most 16") reads stricter than that. Why: every number in the spec was measured with the flood fill (`logo-tone-r2/rule.mts`), and the stricter reading would split a gradient. Cost if wrong: none measured; the fixture test pins the flood fill.
2. What: the making rule lives in `logoCopies.ts`, beside `logoTone.ts`, although the spec says one file. Why: a no to decision 1 is then the removal of one file and its test. Cost if wrong: one more import.
3. What: two templates may name the same file when their grounds differ. The spec's contract says a file name appears once in a request, and its section 3 says the stored file serves both grounds when it shows on both. A stored file that is the canvas file and also serves the other ground needs two templates of one file. The schema refuses two templates of one file on one ground, and a compare file that is also in a template. Why: brightness correlation is signed, so the stored file over a dark ground does not match the same file drawn on a light picture. Cost if wrong: none; without it such a client gets no second search.
4. What: `LocateResult` gains `stamp?: Rect`, present only when the named file's shape differs from the matched file's: the same center and width, the height from the named file's own proportions. The worker stores `stamp` as `logo_rect` when it is there. Why: finish resamples the file to the rectangle, and a website file may differ from the stored file by up to 5% in proportions (same-logo test 1), so it would be stamped stretched. Cost if wrong: one optional field that stays unused until a website file is in a set.
5. What: in `post-logos`, when the matched search is a person's file, the post shows that file and nothing is measured, as locate does. The spec only says such a template is never compared. Cost if wrong: a person's file can become the canvas file of a lifecycle row when the client's posts match it, which is the file a person put there.
6. What: a found logo with no pixel outside its rectangle to sample gives `found: false`. Why: `PostLogo` needs a ground for a found post. Cost if wrong: none at the sizes searched.
7. What: `jobLogos` treats a set whose second file came from a person as current only while the row's `person` key still names that file for that logo. Why: after Remove the file is still in the set until the next settle. Cost if wrong: for about a minute after a Remove, designs start with one file, as today.
8. What: a signed-in person changes `logo_set` only through `set_design_logo_other`. The mark-person trigger puts back the stored `logo_set` on any other write by a signed-in person. Why: the spec makes `settle_design_logo_set` service role only, yet the table's own UPDATE grant lets a staff session write the column. Cost if wrong: one branch in a trigger.
9. What: `set_design_logo_other` takes only a path that starts with `<client id>/design-settings/logo-other-` and ends with `.png`, and refuses a Claude connector session, as the other functions a person may call do (`20261109130000_sprout_brand_declines.sql:83`). ## The making rule, as ordered steps

This is spec section 3 in the order the code runs it. Words: ink is alpha of 16 or more; a part's ink is the sum of its pixels' alpha over 255; a small part has under 1% of the file's ink; a color shows on another at a contrast of 3 or more (`contrast` in `designSettings.ts`); light is #FFFFFF and dark is #0B0E1A.

A. Parts. Scan pixels row by row from the top left. An ink pixel with no part starts one. Grow it over edge neighbors (never corners) that are ink and within 16 per channel of the pixel they are reached from. The part's color is the alpha-weighted average of its pixels, rounded. A part is exposed when one of its pixels is beside a pixel without ink or on the file's edge. For each part, count the pixel edges it shares with each other part.

B. Figures. For a ground, sort the exposed parts by contrast with it, lowest first, equal ones by part number. Walk the list adding ink. The figure is the contrast of the part at which more than 10% of the exposed ink has been passed (0 for a file with no exposed part). The own ground is light when the light figure is at least the dark figure. `both` is true when the figure on the other ground is 3 or more.

C. The copy for the other ground. G is the ground that is not the file's own, I is white for dark and #0B0E1A for light, J is the other of the two.

1. Each whole exposed part: when its color does not show on G it takes I. It is settled either way.
2. Whole inside parts, repeated until nothing changes: in part-number order, take one that is not settled and touches a settled whole part. The part around it is the settled whole part it shares the most edges with (equal: the lower number). If that part was turned and the inside part does not show on its new color, the inside part takes I when I shows on that new color, else J. It is settled either way.
3. A whole part still unsettled is treated as in step 1.
4. Small parts, largest first (equal: the lower number), repeated until nothing changes: one that touches a settled part is on the side of the settled part it shares the most edges with (through other small parts, the whole part at the end) and takes what that whole part came to: its new color when it was turned, its own color when it was kept. Changed after review (Ruling 42): a small part that also touches the side of another whole part, where the two came to different outcomes, is painted pixel by pixel. A pixel that is a blend of the two parts' old colors (within 16 per channel of the closest point on the line between them) gets the same blend of their new colors; any other pixel there takes its side's outcome.
5. Small parts still unsettled form groups joined to each other. A group's color is its largest member's (equal: the lower number). When that color does not show on G, every member takes I.

D. The white copy: C with G dark and I white, except that steps 1, 3 and 5 turn every part they reach.

E. Painting. Every pixel of a turned part takes the part's new color. Alpha is never written.

F. Dropping. Between two colorings, a whole part has changed when any channel differs by more than 16. The copy for the other ground is dropped when the changed whole parts hold under 1% of the ink against the stored file. The white copy is dropped when that is true against the stored file, or against a kept copy for the other ground.

Exact behavior:

- `sameLogo`, four tests, all must hold: (1) the smaller width-to-height ratio is at least 0.95 of the larger; (2) both are brought with `resampleRGBA` to 256 wide and `round(stored.height * 256 / stored.width)` high, ink is alpha of 128 or more, and shared ink over ink in either is at least 0.9; (3) `ownGround` of the file is the other ground of the stored file's; (4) the file is at least as wide as the stored file. `overlap` is the number of test 2.
- `colorGap`: the file is brought to the rectangle's size with `resampleRGBA`; over its pixels with alpha of 128 or more that fall inside the picture, the mean of `Math.hypot` of the three channel differences. `Infinity` when no such pixel exists.
- `groundAround`: the rectangle widened by `round(width * 0.25)` on each side and `round(height * 0.5)` above and below; from its top left corner every second pixel on every second row, inside the picture and outside the rectangle; sorted by 0.299 red + 0.587 green + 0.114 blue, equal ones by position; the pixel at index `length >> 1` is the ground; `flat` is the share of the sampled pixels within 16 per channel of it. Null when nothing was sampled.
- `searchTemplates`: for each template, `usual = canvasLogoRect(placement, file width, file height, picture width, picture height)` and `findLogo(..., usual, ground, { scales })`. The better score wins, the first template's when equal. `scores` are in the order sent.
- `nameFile`: when the matched template is `fixed`, the answer is its file with empty `gaps`. Otherwise the candidates are the matched template's file, the other template's file when it is not `fixed`, and the compare files, each file name once. Each gets `colorGap` at `found.rect`. The smallest wins; equal ones go to the earliest in `order`.
- `stampRect`: null when the two rasters have the same width and height. Otherwise `{ width: rect.width, height: round(rect.width * named.height / named.width), x: rect.x, y: round(rect.y + rect.height / 2 - height / 2) }`.

```sql
-- B1: take the sets away, keep a person's file
update design_brand_settings
   set logo_set = case when logo_set ? 'person' then jsonb_build_object('person', logo_set->'person') end
 where logo_set is not null;
-- B1 check: 0
select count(*) from design_brand_settings where logo_set ? 'of';
-- B2 check: 0
select count(*) from canva_finish_jobs where status in ('queued', 'running') and input ? 'logos';

-- B5: the step rows' keys as the old runner computes them
update client_lifecycle_steps
   set inputs_key = regexp_replace(inputs_key, '\|site:.*$', '')
 where step = 'design_settings' and inputs_key like 'refs:%';
update client_lifecycle_steps
   set inputs_key = 'person'
 where step = 'design_settings' and inputs_key like 'person|%';
-- B5 key check: 0
select count(*) from client_lifecycle_steps
 where step = 'design_settings' and inputs_key is not null and inputs_key <> 'person'
   and inputs_key !~ '^refs:[^|]*\|logo:[^|]*\|colors:[^|]*$';
```

Why B5 exists, and what it costs to skip it. After the new runner has run, every `design_settings` step row holds the new key (`…|site:…|other:…|tone:1`, or `person|…`). The old runner computes the old key (`refs:…|logo:…|colors:…`, or `person`), would see changed inputs for every client, and would run its old step: one paid model read of the logo's spot for each lifecycle client with posts (12 lifecycle rows are live on 16 Nov) and a rewrite of `logo_path`, `placement`, `background` and `derived`. The statements run a second time after the deploy because a look of the new runner between the first run and the deploy writes the new key again. One cost stays: a step row that is waiting or failed at that moment (its set was being made) is run by the old runner when its time comes, which is one model read for that client. The runner is therefore taken back only when the fault is in the lifecycle step itself. For a fault anywhere else B1 to B4 are the whole way back and the runner stays: with the sets taken away and `design-request` old, the sets it makes are read by nothing.

A way back for one function alone (the worker, say) is a commit that reverts only that function's files and never anything under `server/`, so the service stays new. B1 and B2 come first there too when the function is `design-request` or the worker.
